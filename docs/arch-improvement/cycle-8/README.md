# Исследование перехода локального Durable на Zero

Статус: **терминальная основа установлена изолированно и открыта в Rex**. Для навыков и скрытия отключённых панелей собран отдельный новый кандидат; его актуальные проверки описаны в [follow-up](capability-followup.md). Уже открытая вкладка не обновлялась; совместная приёмка нового кандидата и глобальное переключение ещё впереди.

## Цель пользователя

Локальный Durable должен работать на общей основе Durable Zero, а не использовать отдельные заимствованные части. Здесь создаём и тестируем свои отдельные workspace-пакеты, подключённые к Zero через поддерживаемые интерфейсы. Zero остаётся основой, upstream — в своём GitHub-репозитории. Изменения исходников Zero допустимы для подтверждённых исправлений и обоснованных архитектурных улучшений. Перед таким изменением необходимо объяснить проблему, границы решения и способ проверки; патчи ради самого факта патча не нужны.

Сначала необходимо сделать работающую терминальную сборку Durable на Zero. Перенос существующих Durable-расширений начинается только после проверки этой основы. После локальных проверок и проверки установленного кандидата Zero-сборка должна стать основным глобально установленным Pi Durable. Исходное исследование только фиксировало этот порядок. В продолжении реализации установлен изолированный кандидат; основная команда ещё не переключена.

## Что уже установлено

1. **Zero — headless-сборка над native Pi Durable Harness.** Coordinator не заменяет native модельный цикл. Runner собирает конкретные зависимости; adapter-pi-durable открывает Harness и SQLite.
2. **У Zero нет одного обязательного «нового формата расширений».** Обычные Pi extensions и assembly-level BuiltinExtension решают разные задачи. Формат переноса надо выбирать по владельцу поведения.
3. **В baseline не было полной терминальной совместимости.** Новый UI-пакет сохраняет установленный редактор и карточки, используя native view/controller. Это не означает готовность UI-контрактов всей коллекции расширений.
4. **Текущий checkout Host и установленная команда — разные кандидаты.** `~/.local/bin/pi-durable` запускает закреплённый release launcher, который использует DpiClient и системный Host service.
5. **Нельзя объединять две iii-интеграции по общему имени.** BB→ACP→native iii Harness отличается от iii worker, который управляет уже открытым Pi Harness.

Источники и ограничения проверки приведены в двух отчётах выше. Здесь не утверждается работоспособность установленного сервиса или полная совместимость расширений.

## Архитектурное направление

Это целевая схема для проверки, а не описание уже выполненной миграции:

```text
терминальный UI ── host adapter ──┐
BB UI ────────── BB adapter ─────┼── единая сборка Zero
HTTP/SSE Host ─ service adapter ─┘      │
                                      ├── Core: coordinator + policy + ports
Pi extensions ─ extension loader ──────┤
assembly builtins ─ composition root ──┤
iii → Pi bridge ─ runtime adapter ─────┤
                                      └── PiDurableEngine
                                            └── native Harness / SQLite / tools

BB → ACP → native iii Harness — отдельная система, не Pi extension.
```

«Единая сборка» не означает один процесс для всех пользователей. Это общий состав runtime и один физический владелец каждой открытой сессии. Выбор межпроцессного транспорта не переносит владельца Harness в терминал или BB.

### Правила границ

- Core определяет собственные порты и не импортирует BB, UI, iii SDK, SQLite или Earendil runtime.
- Конкретные ресурсы, окружения, builtins и host bindings связывает composition root.
- Модельный цикл, native submissions, task graph и долговечное состояние остаются у native Harness.
- UI-адаптер отображает проверенные события и выполняет настоящие взаимодействия. Пустые callbacks не считаются совместимостью.
- Между receipt, завершением запроса и отображённым ответом сохраняется различие.
- Текущие пользовательские сессии и установленный runtime не переключаются в рамках этого исследования.

## Что переносить первым

Уточнённый пользователем первый результат — терминальная сборка Durable на Zero без переноса нашей коллекции расширений. Она должна включать ввод, streaming, встроенный native инструмент, завершение, abort и повторное открытие тестовой сессии. После проверки этой основы начинается перенос расширений.

Для первого результата нужны хостовая композиция и терминальный адаптер. Пользователь подтвердил: runtime должен продолжать активную работу после отключения терминала и позволять повторное подключение без повторной отправки запроса. Выбран отдельный runtime с приватным Unix-сокетом. Сохранение истории в SQLite само по себе не доказывает продолжение активной работы.

Требуется сохранить прежний редактор, оформление и карточки инструментов установленного Pi Durable. Новый readline-клиент служит только диагностической пробой. Полноценный интерфейс подключается через отдельный UI-пакет; после проверок тестовую сессию необходимо открыть в существующем Rex пользователя.

Необходимо согласовать реально используемые session/UI controls и точный runtime/SDK baseline. Полную совместимость UI расширений и перенос всех компонентов в BuiltinExtension не включаем в первый результат.

Для сравнения:

| Подход | Оценка |
|---|---|
| Копировать отдельные файлы Zero в прежние runtime | Не достигает цели пользователя; сохраняет несколько расходящихся реализаций |
| Переписать все расширения в BuiltinExtension | Смешивает пользовательскую функциональность с native assembly; создаёт лишний перенос |
| Общая сборка Zero + ограниченные host adapters + классификация расширений | Предпочтительный путь; незакрытые host contracts должны быть реализованы и проверены, а не скрыты |

## Проверки и незакрытые пункты

**Проверки:** начальные результаты исследования сохранены в исходных отчётах. Актуальные build/typecheck/native/PTY-проверки записываются в [терминальном отчёте](terminal-runtime.md). Зависимости установлены через кешированный pnpm в обход неисправного Corepack; глобальное окружение не менялось.

**CodeGraph:** пользователь сообщил о текущей индексации. При проверке рабочей папки индекс ещё отсутствовал; повторный запуск не выполнялся. Существующие индексы других проектов использовались только как навигация с проверкой текущих исходников.

**Прежняя установка:** исходное исследование опиралось на исходники, package manifests и безопасные пути запуска. Позднее выполнены отдельные native/PTY/installed-проверки и настоящий модельный запрос в новой сессии Rex. Их результаты не означают миграцию старых пользовательских сессий.

**Открыто:** точное значение термина «DKP» не установлено. В проверенных Host/terminal исходниках такой компонент не найден; нельзя автоматически заменить этот термин на SDK.
